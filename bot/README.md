# בוט כתוביות עברית (Zovex Sub)

userbot בטלגרם שמקבל סרטון בכל שפה ומחזיר **קובץ SRT בעברית ברמת אולפן**,
ואופציונלית גם וידאו עם כתוביות צרובות (עד 10 דקות, צריבה קלה ומהירה).

## איך זה עובד

| שלב | כלי | מה קורה |
|---|---|---|
| 1 | ffmpeg | חילוץ אודיו FLAC 16kHz מונו, וחיתוך לחלקים אם צריך |
| 2 | Groq `whisper-large-v3` | תמלול עם חותמות זמן ברמת סגמנט ומילה + סינון "המצאות" על שקט |
| 3 | Gemini + חיפוש Google | מעבר חקר: נושא, דוברים ומגדריהם, אל מי פונים, שמות, מונחים, אימות ציטוטים |
| 4 | Gemini | תרגום/עריכה בחלונות, עם מסמך החקר כקונטקסט — התאמה 1:1 לשורות המקור |
| 5 | Gemini | בקרת איכות על כל הכתוביות יחד: זכר/נקבה, עקביות מונחים, מספרים |
| 6 | — | בניית SRT: תזמונים ללא חפיפות, מהירות קריאה, פיצול שורות עברי |
| 7 | ffmpeg | צריבה אופציונלית: `preset veryfast`, CRF 28, thread אחד, עד 720p |

**למה הזכר/נקבה יוצא נכון:** ההחלטה מי הדובר ואל מי הוא פונה מתקבלת **פעם
אחת על כל הסרטון** במעבר החקר, ואחר כך כל שורה מתורגמת לפי ההחלטה הזו —
במקום שהמודל ינחש מחדש בכל שורה. מעבר הבקרה בסוף סורק את כל הכתוביות
יחד ומתקן התאמות מגדר שנשברו באמצע.

> **להתקנה מאפס על שרת חדש, כולל חשבון טלגרם ומפתחות חדשים —
> ראו [INSTALL.md](INSTALL.md), שכולל גם מדריך שימוש, ניהול וכוונון.**

## התקנה על שרת לינוקס

```bash
# 1. תלויות מערכת (ffmpeg + פונט עברי לצריבה)
sudo apt update
sudo apt install -y ffmpeg python3-venv python3-pip fonts-noto-core
sudo apt install -y fonts-noto-hebrew || true   # לא קיים בכל ההפצות; fonts-noto-core מספיק
fc-cache -f
fc-list | grep -i hebrew | head -3              # לוודא שיש פונט עברי לצריבה

# 2. הקוד
sudo mkdir -p /opt/zovexsub && sudo chown "$USER" /opt/zovexsub
git clone -b ccr-7e9ba85e-p9u399 https://github.com/davidggjg/zovex-android /opt/zovexsub/repo
ln -s /opt/zovexsub/repo/bot /opt/zovexsub/bot

# 3. סביבה וירטואלית
python3 -m venv /opt/zovexsub/venv
/opt/zovexsub/venv/bin/pip install -r /opt/zovexsub/bot/requirements.txt

# 4. הגדרות — כאן נכנסים המפתחות (לא בגיט!)
cp /opt/zovexsub/bot/.env.example /opt/zovexsub/bot/.env
nano /opt/zovexsub/bot/.env
chmod 600 /opt/zovexsub/bot/.env

# 5. התחברות ראשונה לחשבון (מספר טלפון + קוד). מריצים פעם אחת באופן ידני:
cd /opt/zovexsub/bot && /opt/zovexsub/venv/bin/python -m zovexsub.bot
```

`TG_API_ID` ו-`TG_API_HASH` נלקחים מ-https://my.telegram.org ← API development tools.

### הרצה כשירות

```bash
sudo cp /opt/zovexsub/bot/zovexsub.service /etc/systemd/system/zovexsub.service
sudo sed -i "s/User=%i/User=$USER/" /etc/systemd/system/zovexsub.service
sudo systemctl daemon-reload
sudo systemctl enable --now zovexsub
sudo journalctl -u zovexsub -f
```

### גודל הכתוביות

ברירת המחדל היא `קטן`. בתשובה לאישור הצריבה אפשר לבקש גודל אחר:

```
כן            קטן (ברירת מחדל)
כן בינוני
כן גדול
```

לשינוי ברירת המחדל לכולם: `SUB_SIZE=בינוני` ב-.env.

### הורדה מיוטיוב

הדרך המומלצת היא cobalt — שרת הורדה קטן שרץ אצלנו בקונטיינר אחד, בלי
מפתחות ובלי חשבון. האתר הציבורי שלהם כיבה את יוטיוב, אבל התקנה עצמית
עדיין עובדת, וזה בדיוק ההבדל.

```bash
docker run -d --name cobalt --restart unless-stopped \
  -p 127.0.0.1:9000:9000 \
  -e API_URL=http://127.0.0.1:9000 \
  ghcr.io/imputnet/cobalt:11
```

ואז ב-.env:

```
COBALT_URL=http://127.0.0.1:9000
```

הבוט ינסה אותו ראשון, וייפול ל-yt-dlp אם הוא לא זמין או מסרב.

#### המסלול הישן: yt-dlp ישירות

יוטיוב חוסמים אותו מכתובות של שרתים, ולכן נדרשים שלושה דברים:

```bash
# גרסת הלילה — היציבה לא מצליחה לקרוא את הנגן של יוטיוב
/opt/zovexsub/venv/bin/pip install -U --pre "yt-dlp[default]"

# סביבת JavaScript, ש-yt-dlp דורש עכשיו ליוטיוב
curl -fsSL https://deno.land/install.sh | sh
```

ועוגיות מחשבון מחובר, אחרת יוטיוב מחזיר "Sign in to confirm you're not
a bot". מייצאים אותן מהדפדפן בתוסף לפורמט Netscape, מעתיקים לשרת,
ומוסיפים ל-.env:

```
FETCH_COOKIES=/opt/zovexsub/cookies.txt
```

בלי העוגיות ההורדה תיכשל — אבל עם הודעה שמסבירה בדיוק מה חסר, במקום
שגיאה גולמית.

### מודל זיהוי הדיבור

בלי המודל המערכת מזהה דיבור לפי עוצמת קול, ואז מוזיקת רקע נספרת כדיבור
והכתוביות לא מוצמדות נכון. נמדד על קובץ שבו הדיבור תופס 22% מהזמן:
זיהוי לפי עוצמה החזיר 85% דיבור, Silero החזיר מוזיקה 0-3% ודיבור 96%.

```bash
sudo mkdir -p /opt/zovexsub/models
sudo curl -L -o /opt/zovexsub/models/silero_vad.onnx \
  https://raw.githubusercontent.com/snakers4/silero-vad/master/src/silero_vad/data/silero_vad.onnx
/opt/zovexsub/venv/bin/pip install onnxruntime numpy
```

2.3MB, רץ על מעבד, 192x זמן אמת על ליבה אחת — סרט של שעתיים וחצי
בפחות מדקה.

### איפה הלוגים

בשרת הייעודי קובץ ה-service מפנה את הפלט לקובץ, לא ל-journal. לכן
`journalctl` מראה רק את שורות systemd עצמו, ולא את מה שהבוט כותב:

```bash
tail -f /var/log/zovexsub.log          # מעקב חי
grep "dB" /var/log/zovexsub.log        # זיהוי דיבור ושקט
grep -E "מקביל|נכשל" /var/log/zovexsub.log
```

## שימוש

**סרטון לבד לא מפעיל כלום.** שולחים סרטון, ואז **מגיבים להודעה של הסרטון** עם `.srt`.

הפקודה חייבת להתחיל בנקודה ולהיות המילה הראשונה בהודעה. הודעה רגילה
שמזכירה "כתוביות" או "srt" באמצע משפט לא מפעילה כלום, והבוט אינו מגיב
לשיחות שאינן מופנות אליו.

אפשר גם לשלוח קישור במקום קובץ: `.srt https://...` — הבוט מוריד את הווידאו
בעצמו דרך yt-dlp (יוטיוב, videa.hu ומאות אתרים אחרים), ומעלה את התוצאה
לטלגרם. אותן סטטיסטיקות התקדמות בכל השלבים.

הבוט מתמלל, שולח את קובץ ה-SRT, ואז — **רק אם הסרטון קצר מ-10 דקות** —
שולח הודעה נפרדת: "רוצה שאצרוב את הכתוביות על הסרטון?". מי שרוצה משיב
לה `כן`, ורק אז הצריבה מתחילה. **אין צריבה אוטומטית**, גם לסרטון קצר.

סרטון מעל 10 דקות: נשלח SRT, ובמקום ההצעה נשלחת הודעה שצריבה לא זמינה באורך הזה.

הצעת צריבה שלא נענתה תוך חצי שעה פגה, והקבצים הזמניים נמחקים מהשרת.

רק משתמשים ברשימת המורשים (ואתה) יכולים להפעיל. מי שלא מאושר — הבוט מתעלם ממנו לגמרי.

### צריבה של כתוביות קיימות

מי שכבר יש לו קובץ `.srt` — ערוך ידנית או מהרצה קודמת — לא צריך לתמלל שוב:

1. מגיבים לסרטון עם `.srt צריבה`
2. הבוט מבקש את הקובץ
3. שולחים את ה-`.srt` **בתגובה להודעה שלו**
4. הצריבה מתחילה

אפשר גם לקצר: שולחים את קובץ ה-`.srt` עם הכיתוב `.srt צריבה`, בתגובה
לסרטון, והצריבה מתחילה מיד. נתמכים `.srt`, `.vtt`, `.ass` ו-`.ssa`.

בקשה שלא נענתה תוך חצי שעה פגה.

## ניהול מורשים (רק מהחשבון שלך, נוח בהודעות השמורות)

| פקודה | מה היא עושה |
|---|---|
| `.srt id` בתגובה להודעה של מישהו | מראה שם + **ID** + האם הוא מאושר |
| `.srt הוסף` בתגובה להודעה | מאשר את מי ששלח אותה |
| `.srt הוסף 123456789` | מאשר לפי ID |
| `.srt הסר 123456789` / `.srt הסר` בתגובה | מבטל אישור |
| `.srt רשימה` | כל המאושרים |
| `.srt ניהול` | כל פקודות הניהול |

**הדרך הקלה להוסיף מישהו:** מעבירים (Forward) הודעה שלו להודעות השמורות, ומגיבים לה
`.srt הוסף`. הבוט מחזיר את השם וה-ID ומוסיף אותו.

הרשימה נשמרת ב-`allowlist.json` ליד הקוד — לא צריך לערוך `.env` ולא להפעיל מחדש.

## שליטה בעומס השרת

הכול ב-`.env`:

| משתנה | ברירת מחדל | מה זה עושה |
|---|---|---|
| `BURN_MAX_MINUTES` | 10 | מעל זה נשלח SRT בלבד, בלי צריבה |
| `BURN_TIMEOUT` | 1800 | תקרת זמן קשיחה לצריבה בשניות |
| `BURN_THREADS` | auto | ליבות לצריבה — לפי העומס בפועל |
| `RESERVE_CORES` | 1.5 | ליבות שנשארות פנויות לשאר השרת |
| `FFMPEG_THREADS` | 1 | ליבות לחילוץ אודיו וזיהוי דיבור |
| `BURN_PRESET` / `BURN_CRF` | veryfast / 28 | איכות מול מהירות |
| `BURN_MAX_HEIGHT` | 720 | הקטנת רזולוציה לפני צריבה |
| `NICE` | 15 | עדיפות CPU נמוכה (+ `ionice -c 3`) |
| `MAX_INPUT_MINUTES` | 180 | אורך מקסימלי לתמלול |
| `DISK_FACTOR` / `DISK_RESERVE_GB` | 2.5 / 3 | כמה מקום פנוי נדרש לפני שמתחילים |

בנוסף: **שני תורים נפרדים** — צריבה ארוכה לא חוסמת בקשת כתוביות קצרה;
`systemd` מגביל זיכרון ל-3GB ועדיפות IO ל-idle.

### צריבה מקבילית

מסנן הכתוביות של ffmpeg (`libass`) רץ בחוט אחד ומעבד פריים אחד בכל רגע.
לכן תהליך ffmpeg יחיד אינו מצליח להעסיק מכונה עם הרבה ליבות: המקודד,
גם אם קיבל שמונה-עשר חוטים, ממתין לפריימים שמגיעים בקצב של ליבה אחת.

הפתרון הוא פיצול: הווידאו נחתך לקטעים, כל קטע נצרב בתהליך משלו, וכך יש
צינור רינדור נפרד לכל אחד. נמדד על ארבע ליבות, אותה חומרה ואותן הגדרות:

| | זמן ל-30 שניות וידאו |
|---|---|
| תהליך אחד, ארבעה חוטים | 4,805ms |
| ארבעה תהליכים במקביל | 3,377ms |

פי 1.42, וההפרש גדל ככל שיש יותר ליבות, כי החלק הסדרתי לא משתנה.

האודיו אינו עובר קידוד: הקטעים נצרבים ללא קול והמקורי מוזג בסוף כמו
שהוא, כך שאין סיכון להיסט בין הקטעים. הקרדיט מופיע רק בקטע הראשון.
אחרי ההרכבה נבדקים אורך הפלט והזרמים שבו, וכל חריגה מפילה את הצריבה
חזרה לנתיב התהליך היחיד במקום להחזיר קובץ פגום.

| משתנה | ברירת מחדל | מה זה |
|---|---|---|
| `BURN_SEGMENTS` | 0 | מספר הקטעים. 0 = לפי מספר הליבות |
| `BURN_SEGMENT_THREADS` | 3 | חוטים לכל קטע |
| `BURN_SEGMENTS_MAX` | 8 | תקרה |
| `BURN_PARALLEL_MIN_MINUTES` | 3 | וידאו קצר מזה נצרב בתהליך אחד |

על מכונה של 18 ליבות זה נותן 6 קטעים של 3 חוטים — כל הליבות מועסקות.

### חלוקת מעבד עם שאר השרת

שתי שכבות עובדות יחד.

`nice 15` ו-`ionice -c 3` הן השכבה הדינמית: מתזמן הליבות נותן לצריבה רק
את מה שפנוי, וברגע שתהליך אחר מבקש מעבד הוא מקבל אותו והצריבה נדחקת.
זה קורה ברזולוציה של אלפיות שנייה.

`BURN_THREADS=auto` היא השכבה השנייה: בתחילת כל צריבה נבדק העומס בפועל,
ונבחר מספר ליבות שמשאיר `RESERVE_CORES` פנויות. על שרת של עשר ליבות:

| עומס | threads |
|---|---|
| 0.1 | 8 |
| 2.0 | 6 |
| 4.0 | 4 |
| 6.0 | 2 |
| 8.5 | 1 |

כך שבשעה שקטה הצריבה מנצלת כמעט את כל המכונה, ובשעת עומס היא מצטמצמת
מעצמה. בכל מקרה רצה צריבה אחת בלבד, דרך תור נפרד.

### למה לא פשוט לקודד מהר

נמדד על מקור גרעיני 1080p, ארבע ליבות, 60 שניות וידאו:

| הגדרה | מהירות | גודל פלט |
|---|---|---|
| H.264 ultrafast CRF23 | 1.53x | 632MB |
| H.265 veryfast CRF30 | 0.98x | 21MB |

הקידוד המהיר חוסך כשליש מזמן הקידוד ומנפח את הפלט פי שלושים. בחישוב זמן
כולל, בהנחת העלאה של 10MB לשנייה, הוא יוצא איטי יותר: 40 שניות קידוד
ועוד 63 העלאה מול 61 ועוד 2. לכן `quick` מוגבל לסרטונים קצרים בלבד
(`QUICK_UNDER_MB`, ברירת מחדל 300MB), ולא משמש כברירת מחדל לקבצים גדולים.

### מה זה באמת עולה

נמדד על מכונת 4 ליבות, מקור 1080p גרעיני (המקרה הקשה), יעד 720p עם
כתוביות צרובות:

| threads | מהירות | שעתיים וחצי וידאו | גודל פלט |
|---|---|---|---|
| 1 | 0.71x | 3.5 שעות | זהה |
| **2** | **1.68x** | **1.5 שעות** | זהה |
| 4 | 2.52x | שעה | זהה |

מספר ה-threads לא משנה את גודל הפלט או את האיכות — רק את משך החלון. על
תוכן דיגיטלי נקי המהירות גבוהה פי שלושה בערך.

שינוי `preset` או רזולוציה כמעט לא עוזר על תוכן גרעיני (0.71x מול 0.95x
בין veryfast 720p ל-ultrafast 480p), כי הצוואר הוא פענוח המקור ולא
הקידוד. `ultrafast` גם מכפיל את גודל הפלט, מה שמייקר את ההעלאה.

חילוץ האודיו וזיהוי הדיבור זניחים (פי מאה מהזמן אמיתי), והתמלול והתרגום
רצים אצל Groq ו-Google ולא על השרת.

## קרדיט פתיחה

הווידאו הצרוב נפתח בקרדיט שמוצג עשר שניות, עם מעבר רך פנימה והחוצה.
הטקסט נשלט ב-`CREDIT_TEXT` (שורות מופרדות ב-`|`), האורך ב-`CREDIT_SECONDS`
והגודל ב-`CREDIT_SIZE`. ערך ריק מבטל אותו.

הקרדיט נכתב כקובץ ASS נפרד ולא כטקסט שמצויר על הווידאו, כי libass מטפל
נכון בכיווניות של העברית בעוד ש-drawtext היה מציג את האותיות הפוכות.

## מהירות מול טלגרם

שני צווארי בקבוק טופלו כאן.

**הצפנה.** כל בייט שעובר מול טלגרם מוצפן ב-AES. בלי החבילה `cryptg` זה
נעשה בפייתון טהור. נמדד על מכונה זו:

| מימוש | קצב |
|---|---|
| פייתון טהור | 0.4MB/שנייה |
| `cryptg` (קוד C) | 68MB/שנייה |

פי 170. בלי `cryptg`, קובץ של 686MB מבזבז כ-28 דקות על פענוח בלבד, בלי
קשר למהירות הרשת. החבילה נמצאת ב-`requirements.txt`, והבוט מתריע בלוג אם
היא חסרה.

**סדרתיות.** טלתון מבקש חלק, ממתין, מבקש את הבא. `TG_CONNECTIONS`
(ברירת מחדל 4) מריץ כמה בקשות במקביל בשני הכיוונים. אם המסלול המהיר
נכשל מכל סיבה, המערכת נופלת חזרה למימוש הרגיל של טלתון.

## מפתחות API

`GROQ_API_KEYS` ו-`GEMINI_API_KEYS` מקבלים **כמה מפתחות מופרדים בפסיק**.
כל מפתח הוא חשבון נפרד עם מכסה משלו, ולכן מפתחות נוספים אינם רק גיבוי
אלא תפוקה: המערכת מתמללת קטע לכל מפתח Groq במקביל, ומתרגמת חלון לכל
מפתח Gemini במקביל. גם חלוקת האודיו מתאימה את עצמה — ככל שיש יותר
מפתחות, הקטעים קצרים יותר כדי שכולם יעבדו בו-זמנית:

| מפתחות | קטעים לשעת וידאו | אורך קטע |
|---|---|---|
| 5 | 5 | 12 דקות |
| 10 | 10 | 6 דקות |
| 15 | 15 | 4 דקות |

מפתח שחוזר עם 429 נכנס לקירור ולא נבחר עד שהוא משתחרר. אפשר להוסיף או
להסיר מפתחות בכל שלב — רק `.env` ואתחול השירות.

כש-Groq נכשל על קטע, גם במודל הגיבוי, Gemini מתמלל אותו. נמדד שהסטייה
בתזמונים שלו היא כשתי עשיריות שנייה לעומת מאית אצל Whisper, ולכן זה
גיבוי בלבד — וההקשבה החוזרת מדייקת אותו אחר כך.

⚠️ מפתחות נשמרים **רק** ב-`.env`, שנמצא ב-`.gitignore`. מפתח שנחשף — החליפו אותו.
