# מצב המערכת — מה שידוע, ולמה

הקובץ הזה קיים כי שיחות נדחסות ואז נשכחות החלטות. **לקרוא אותו לפני
שמשנים משהו בהורדה, במסירה או בתזמוני הכתוביות.**

כלל ברזל שנלמד ביוקר: **לא להסתמך על ברירות מחדל בקוד.** ה-`.env`
בשרת דורס אותן, ושלוש פעמים ברצף נקבעו כאן אבחנות שגויות כי נקראה
ברירת המחדל במקום הערך האמיתי. לבדיקה:

```bash
cd /opt/zovexsub/repo/bot && /opt/zovexsub/venv/bin/python -c \
"from zovexsub import config as c; print(c.TG_PIPELINE, c.TG_INFLIGHT_MAX)"
```

## מבנה

| רכיב | מה הוא |
|---|---|
| `/opt/zovexsub/repo` | ספריית הגיט (לא `/opt/zovexsub`) |
| `/opt/zovexsub/repo/bot/.env` | ההגדרות שהקוד באמת קורא (`config.py:7`) |
| `/var/log/zovexsub.log` | הלוג. **לא** ב-journal |
| `tg-bot-api` (Docker) | שרת ה-Bot API המקומי, פורט 8081 |
| `/opt/zovexsub/deploy.sh` | פריסה: pull, בדיקות, המתנה לצריבה, הפעלה מחדש |

**לקוח הבוט אינו מבקש עדכונים — שרת ה-Bot API המקומי עושה זאת.**
אם הקונטיינר `tg-bot-api` לא רץ, הבוט מחובר אך לא מקבל שום הודעה,
והלוג שותק לגמרי בלי שגיאה. זה קרה פעמיים ונראה כמו "הבוט מת".

## שני החשבונות

| | מי | למה |
|---|---|---|
| הורדה | **Premium בלבד**, בכל גודל | התיעוד הרשמי: חשבון Premium אינו יכול לקבל `FLOOD_PREMIUM_WAIT` |
| מסירה | **חשבון תמיד** דרך ערוץ האחסון, הבוט גיבוי | מסלול אחד לכל גודל |
| מסירה מעל 2GB | חייב חשבון; אין גיבוי | תקרת הבוט |

העברה בערוץ אינה העלאה, ולכן תקרת הבוט אינה חלה עליה.
`access_hash` של ערוץ הוא **פר-חשבון** — המטמון ב-`botapi._storage`
חייב להישאר לפי `id(client)`.

| דיסק | 9.33 מתוך 170GB | "botapi-data מתמלא" |

## הצוואר האמיתי שנמצא

ה-`.env` הכיל שלוש דריסות שיחד נתנו **48MB באוויר** — בדיוק מה שמייצר
`FLOOD_PREMIUM_WAIT`. הלקוח הרשמי של טלגרם לא עובר 16MB.

| | היה | עכשיו |
|---|---|---|
| `TG_PIPELINE` | 3 | 1 |
| `TG_INFLIGHT_MAX` | 48 | 16 |
| `FETCH_CONNECTIONS` | 4 | 8 |

אחרי התיקון: 1.91GB הגיע ל-60% בכחצי דקה (לפני כן 3–7MB/s).

## מספרי הלקוח הרשמי (נקראו מהמקור, לא מדוח)

`Telegram/SourceFiles/storage/download_manager_mtproto.{h,cpp}`:
`kDownloadPartSize = 128*1024`, `kStartSessionsCount = 1`,
`kMaxSessionsCount = 8`, `kStartWaitedInSession = 4`,
`kMaxWaitedInSession = 16` → תקרה של 16MB באוויר.
הוא גם **מוריד** סשנים אחרי כשלונות (`kRemoveSessionAfterTimeouts = 4`).

## טעויות שנעשו כאן — לא לחזור עליהן

1. **`TG_MEDIA_DC`** — התיעוד מחייב לשלוח קבצים לכתובת `media_only`,
   אבל הוא **לא** אומר שאותו `auth_key` תקף שם. ההנחה הזאת הפילה את
   המסלול ל"לא התחיל להוריד תוך 240 שניות". כבוי כברירת מחדל.
2. **`DOWNLOAD_FIRST=bot`** — נקבע מהנימוק שעונש ההעלאות חל על החשבון.
   התיישן ברגע שההורדות עברו ל-Premium. עכשיו `account`.
3. **`bufsize`** — `cap*2` על סרטון של 26 שניות חרג מ-32 ביט והפיל את
   ffmpeg. ההגנה היחידה הייתה `duration <= 0`. עכשיו יש `BITRATE_CAP_MAX`.
4. **צריבה כפולה** — כשל בהרכבה הפיל ישר לתהליך יחיד, שצרב הכל מחדש.
   עכשיו ניסיון שני מדלג על קטעים קיימים.

## פתוח

- למה קונטיינר `tg-bot-api` נופל (`docker logs tg-bot-api`)
- להחליף `api_hash` ב-my.telegram.org — הודפס בצ'אט
- להחליף את ה-URL השבור של מדידת המהירות ב-`deploy.sh`
- `invokeWithTakeout` — מתועד, אך דורש אישור של עד 24 שעות

## פקודות

```bash
bash /opt/zovexsub/deploy.sh                      # פריסה
docker start tg-bot-api                           # הבוט שותק
tail -40 /var/log/zovexsub.log                    # מה קרה
cd /opt/zovexsub/repo && git checkout $(cat /opt/zovexsub/GOOD) && \
  cp /opt/zovexsub/env-good bot/.env && systemctl restart zovexsub
```
